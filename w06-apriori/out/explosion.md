# 지지도와 카운터 증가 실측

실제 기기에서 실행한 측정이다. CPU는 AMD Ryzen 7 9800X3D 8-Core Processor, 설치 RAM은 32GB다. 기존 측정도 같은 컴퓨터에서 수행했음을 확인했다. 측정 당시 별도로 실행 중이던 프로그램은 없었다. 시간은 단일 실행이며 시스템 상태와 계측 비용의 영향을 받을 수 있다.

고정 데이터: bench.build(seed=246), 20,000개 바구니, 2,000개 항목. 지지도 400→1, 총 9개 설정으로 400배 범위를 측정했다. 각 시간은 입력 생성 이후 알고리즘 실행 시간이다. 메모리는 tracemalloc이 관측한 Python 할당 peak이며, 이미 생성된 바구니와 프로세스 전체 RAM은 제외한다.

## A2: 어디서 중단했는가

support=1까지 완료했다. 가장 큰 측정은 4.154초, 327.024 MB였다. 이 데이터에서는 RAM 부족이나 견디기 어려운 지연이 발생하지 않았다. support는 양의 정수이므로 1보다 낮추어도 새로운 양의 지지도 쌍이 생기지 않는다. 따라서 1에서 종료했으며, 메모리 고장점이나 6 GB 한계를 측정했다고 주장하지 않는다. 이 고정 데이터로는 실제 기기의 메모리 한계를 찾을 수 없다는 것이 관찰이다.

## A4–A5: 카운터와 정답의 다른 증가

연속 설정의 카운터 배수는 5.539, 4.669, 2.997, 1.089, 1.000, 1.000, 1.000, 1.000이다. 초반 400→200→100→50에서 5.54배·4.67배·3.00배로 증가해 두 배보다 가파르다. 이후 항목이 대부분 살아남아 카운터는 893,456개에서 포화한다. 따라서 계속 지수적으로 늘어난다는 결론은 틀리다.

support 400→50에서 정답은 249→6,397인데 카운터는 10,585→820,259개이다. support=50에서 약 128.2개 카운터를 유지해야 정답 하나를 얻는다. 그러나 support=1에서는 관측된 모든 쌍이 정답이 되어 둘 다 893,456이다. 낮은 문턱이 항상 같은 비율로 더 많은 메모리를 쓰는 것은 아니다. 이 간격이 큰 중간 영역에서 PCY의 필터가 특히 유용하다.


고정 입력에서 support=1까지 도달했으므로 이 실험에서 더 낮출 유효 문턱은 없다. 따라서 기록할 실제 자원 고갈 지점은 없으며, 종료 조건은 메모리 부족이 아니라 모든 관측 쌍이 정답이 되는 문턱의 하한이다. 고정 입력 실험만으로 기기의 RAM 고갈 지점을 추정하지 않는다.

### 추가 실험 · 지지도를 낮추며 중단 지점 확인

고정된 원래 입력에서는 support=1까지 완료됐으므로 바구니 160,000개·항목 16,000개로 확장한 입력을 추가했다. seed=246과 같은 가중 항목 추출·쌍 삽입 규칙을 사용했다. 누적 가중치를 미리 계산하는 생성기는 원래 20,000개·2,000항목 설정에서 기존 생성기와 입력 전체가 정확히 같음을 검사했다. 기존 고정 입력 결과는 그대로 유지했다.

실행 전에 패스당이 아니라 첫·둘째 패스 합계 30초 또는 Python 할당 peak 1GiB(1,073,741,824바이트)를 실용적 중단 기준으로 정했다. 두 번째 패스의 매 100개 바구니마다 확인했다. 입력 생성 시간과 입력 메모리는 제외했다. 아래 시간·메모리는 최종 frozenset 결과 사전 생성 전까지의 카운터 집계 범위다. 기존 표의 최종 결과 사전 생성까지 포함한 peak와 직접 비교하지 않는다.

support=100까지는 완료했지만 50에서 Python 할당 peak가 중단 기준을 넘어 종료했다. 종료 시 두 번째 패스는 145,200/160,000개를 처리했고, 집계 시간은 29.675초, peak는 1,634,131,292바이트(약 1.634GB)였다. 딕셔너리 크기 확장과 100개 단위의 확인 때문에 1GiB를 초과한 순간의 peak를 관측했다. 1GiB 이하로 메모리를 제한한 실험이라는 뜻은 아니다.

support=50의 11,189,164개는 중단 순간의 카운터이며 최종 카운터나 정답 수가 아니다. 최종 정답 수는 계산하지 않았고, 중단한 행으로 카운터 증가율이나 정답 증가율을 계산하지 않았다. 완료한 구간에서는 support 1,600→100에서 카운터가 19,900→5,467,873개로 늘었고 정답은 189→12,355개였다. 문턱을 낮추면서 중간 후보와 시간·메모리 부담이 커진다는 점을 확인했다.

이번에 기록한 한계는 미리 정한 실용적 시간·할당 예산이다. 설치 RAM 32GB를 모두 소진하거나 MemoryError가 발생한 지점은 아니다. 자원 고갈을 관측했다고 주장하지 않으며, 실제로 어디서 어떤 이유로 측정을 멈췄는지를 기록했다.
