# 6주차 관찰 기록

## Task 1: 구현과 규칙의 해석

1패스에서 항목을 세고, 2패스에서는 살아남은 두 항목의 쌍만 센다. 주어진 7개 바구니에서 support=3이면 bread/milk/diaper/beer의 지지도가 모두 5여서 이들 사이 신뢰도는 우연히 대칭이다. 비대칭을 보려면 같은 데이터에서 support=2로 낮춘다. cola→milk는 2/2=1.0, milk→cola는 2/5=0.4다. cola 구매자에 대한 주장이 더 강하지만 표본 2개만으로 일반화할 수 없다.

support=3, confidence≥0.75의 최고 규칙은 beer→diaper 등 신뢰도 0.8, lift=1.12다. 결과 항목의 기본 비율이 5/7이므로 개선은 작다. 인과관계나 강한 연관성을 입증했다고 보지 않는다.

항목 2,000개의 모든 가능한 쌍은 1,999,000개다. 벤치 데이터 support=50에서 빈발 항목은 1,849개이고 가능한 생존 쌍은 1,708,476개다. 실제 바구니에 나타나 딕셔너리에 생성된 카운터는 820,259개다. 가능한 쌍 수와 실제 보유 카운터를 구별해야 한다.

## Task 2: 측정의 한계

CPU는 AMD Ryzen 7 9800X3D 8-Core Processor, 설치 RAM은 32GB다. 기존 측정도 같은 컴퓨터에서 수행했음을 확인했다. 측정 당시 별도로 실행 중이던 프로그램은 없었다.

support=1까지 측정했으며 327.0 MB, 4.15초로 완료되어 실제 RAM 부족은 일어나지 않았다. 데이터의 끝에 도달한 것이며 기기의 한계에 도달한 것이 아니다. 카운터는 초반 문턱 반감마다 5.54→4.67→3.00배 늘다가 893,456개에 포화했다. 정답 수도 결국 같은 수에 도달한다. 세부 표와 그래프 및 계측 범위는 [explosion.md](explosion.md)에 기록했다.

## Task 3: PCY의 이득과 비용

버킷 1,000,003개를 썼다. 정수 배열 array('I')의 본체는 4,000,012바이트이며 카운트는 support에서 포화시켜 overflow를 피한다. 1패스 말에 125,001바이트의 packed bitmap으로 압축한 뒤 정수 배열을 삭제한다. 변환 중 잠시 두 배열이 공존하는 비용도 peak 측정에 포함했다. 항목 Counter, tuple key, dict, 결과 frozenset 등의 비용도 tracemalloc에 포함한다. 입력 바구니, 네이티브 할당, 전체 프로세스 RAM은 제외한다.

동일한 6,397개 정답과 정확한 지지도 값을 유지하며 쌍 카운터는 820,259→13,183으로 약 98.39% 줄었다. 카운터 지표만으로 RAM 절감률을 주장하지 않고 실제 할당도 별도로 재었다.

| 바구니 수 | A-Priori peak(MB) | PCY peak(MB) |
|---:|---:|---:|
| 200 | 0.058 | 4.180 |
| 1,000 | 0.184 | 4.202 |
| 5,000 | 6.428 | 4.234 |
| 20,000 | 102.176 | 4.339 |

이 데이터의 prefix와 고정 support=50에서는 메모리 교차점이 1,000개와 5,000개 바구니 사이에 있다. 정확한 교차점은 측정하지 않았다. 빈발 항목 수·쌍 밀도·support·해시 충돌·버킷 수·Python 객체 크기에 따라 이동한다. 작은 데이터에서는 PCY가 고정 배열 때문에 오히려 불리하고, 시간도 더 걸린다.

| 버킷 수 | 최고 쌍 카운터 | 할당 peak(MB) | 정답 수 |
|---:|---:|---:|---:|
| 1,009 | 820,259 | 102.092 | 6,397 |
| 100,003 | 149,311 | 15.332 | 6,397 |
| 1,000,003 | 13,183 | 4.339 | 6,397 |

1,009개 버킷에서는 충돌로 거의 모든 버킷이 빈발해져 필터가 효과를 잃었다. 버킷 수를 줄이는 것은 공짜 절약이 아니며 2패스 딕셔너리를 키울 수 있다. bench.py는 수정하지 않았다.

## Task 4: 선택 과제 SON

청크별 문턱은 support×청크크기/전체크기이고 크기가 다른 청크에도 그대로 적용했다. 전역 빈발 쌍이 모든 청크에서 문턱 미만이라면 그 지지도를 합해도 support 미만이어야 한다. 전역에서 support 이상이라는 가정과 모순이므로 후보 합집합은 빈발 쌍을 놓치지 않는다. 2패스가 정확한 지지도를 세어 거짓 양성을 제거한다.

| 청크 수 | 후보 수 | 최종 쌍 수 | 누락/추가 | 시간(s) |
|---:|---:|---:|---|---:|
| 3 | 8,817 | 6,397 | 0 / 0 | 0.953 |
| 8 | 14,201 | 6,397 | 0 / 0 | 0.981 |
| 16 | 24,418 | 6,397 | 0 / 0 | 1.044 |

청크를 늘리면 후보 수가 변하지만 최종 정답 6,397개는 유지된다. 후보가 정답보다 많은 것은 1패스의 지역 잡음이며 최종 답의 오류가 아니다. pass two는 후보×바구니의 전수 부분집합 검사 대신 각 바구니의 쌍을 열거하고 후보 set에서 조회한다. 따라서 교재의 느린 구현 시간 12.19초를 내 측정으로 복사하지 않았다. 단일 기기에 들어가는 데이터에서는 기본 A-Priori도 효율적이지만, SON은 청크별 독립 처리와 두 전역 패스로 분산 가능한 구조를 제공한다. 현재 환경에 PySpark가 설치되지 않아 Spark 실행은 생략했다. 단일 프로세스 SON은 구현과 검증을 완료했다.

python task1_apriori.py --verify, python task2_explosion.py --supports 400,200,100,50,25,12,6,3,1, python measure_extra.py, python verify_extra.py, python test_tasks.py. 실행 기록은 out/bench.txt, out/tests.txt, out/verification.txt에 있다.


고정 입력에서 support=1까지 도달했으므로 이 실험에서 더 낮출 유효 문턱은 없다. 따라서 기록할 실제 자원 고갈 지점은 없으며, 종료 조건은 메모리 부족이 아니라 모든 관측 쌍이 정답이 되는 문턱의 하한이다. 고정 입력 실험만으로 기기의 RAM 고갈 지점을 추정하지 않는다.

### 추가 실험 · 지지도를 낮추며 중단 지점 확인

고정된 원래 입력에서는 support=1까지 완료됐으므로 바구니 160,000개·항목 16,000개로 확장한 입력을 추가했다. seed=246과 같은 가중 항목 추출·쌍 삽입 규칙을 사용했다. 누적 가중치를 미리 계산하는 생성기는 원래 20,000개·2,000항목 설정에서 기존 생성기와 입력 전체가 정확히 같음을 검사했다. 기존 고정 입력 결과는 그대로 유지했다.

실행 전에 패스당이 아니라 첫·둘째 패스 합계 30초 또는 Python 할당 peak 1GiB(1,073,741,824바이트)를 실용적 중단 기준으로 정했다. 두 번째 패스의 매 100개 바구니마다 확인했다. 입력 생성 시간과 입력 메모리는 제외했다. 아래 시간·메모리는 최종 frozenset 결과 사전 생성 전까지의 카운터 집계 범위다. 기존 표의 최종 결과 사전 생성까지 포함한 peak와 직접 비교하지 않는다.

| support | 처리한 바구니(2패스) | 보유 쌍 카운터 | 최종 빈발 쌍 | 집계 시간(초) | Python 할당 peak(MB) | 상태 |
|---:|---:|---:|---:|---:|---:|---|
| 1,600 | 160,000 / 160,000 | 19,900 | 189 | 3.789 | 2.438 | 완료 |
| 800 | 160,000 / 160,000 | 94,763 | 584 | 4.396 | 13.338 | 완료 |
| 400 | 160,000 / 160,000 | 505,215 | 1,654 | 6.835 | 51.614 | 완료 |
| 200 | 160,000 / 160,000 | 1,941,259 | 4,535 | 11.246 | 204.826 | 완료 |
| 100 | 160,000 / 160,000 | 5,467,873 | 12,355 | 19.665 | 475.137 | 완료 |
| 50 | 145,200 / 160,000 | 11,189,164 | 미확정 | 29.675 | 1634.131 | 중단 |

support=100까지는 완료했지만 50에서 Python 할당 peak가 중단 기준을 넘어 종료했다. 종료 시 두 번째 패스는 145,200/160,000개를 처리했고, 집계 시간은 29.675초, peak는 1,634,131,292바이트(약 1.634GB)였다. 딕셔너리 크기 확장과 100개 단위의 확인 때문에 1GiB를 초과한 순간의 peak를 관측했다. 1GiB 이하로 메모리를 제한한 실험이라는 뜻은 아니다.

support=50의 11,189,164개는 중단 순간의 카운터이며 최종 카운터나 정답 수가 아니다. 최종 정답 수는 계산하지 않았고, 중단한 행으로 카운터 증가율이나 정답 증가율을 계산하지 않았다. 완료한 구간에서는 support 1,600→100에서 카운터가 19,900→5,467,873개로 늘었고 정답은 189→12,355개였다. 문턱을 낮추면서 중간 후보와 시간·메모리 부담이 커진다는 점을 확인했다.

이번에 기록한 한계는 미리 정한 실용적 시간·할당 예산이다. 설치 RAM 32GB를 모두 소진하거나 MemoryError가 발생한 지점은 아니다. 자원 고갈을 관측했다고 주장하지 않으며, 실제로 어디서 어떤 이유로 측정을 멈췄는지를 기록했다.
