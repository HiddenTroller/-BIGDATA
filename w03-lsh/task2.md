### A4 — 이차 증가 확인

| n → 2n | 실제 시간 배수 | 비교 횟수 배수 |
|---|---:|---:|
| 125 → 250 | 3.971× | 4.016× |
| 250 → 500 | 4.150× | 4.008× |
| 500 → 1,000 | 4.068× | 4.004× |
| 1,000 → 2,000 | 3.985× | 4.002× |
| 2,000 → 4,000 | 4.026× | 4.001× |
| 4,000 → 8,000 | 4.013× | 4.001× |

비교 횟수는 n(n−1)/2이므로 n을 두 배로 늘리면 약 4배가 된다.
큰 n에서 실행 시간도 약 4배로 늘어 O(n²) 증가를 확인했다. 작은 n의 비율은 타이머 정밀도,
캐시, 백그라운드 부하 때문에 더 흔들리므로 비교 횟수와 시간 비율을 함께 본다.

### A7·A8 — 교차점과 LSH의 초기 비용

n=600에서 전수 비교 0.6895s < LSH 0.7884s,
n=650에서 전수 비교 0.7994s > LSH 0.7874s였다.
이번 단일 측정의 첫 역전은 600–650 사이다. 650에서 차이가 작아 정확한 경계를 단정할 수 없고,
1,000에서는 LSH의 우위가 뚜렷하다. 반복 측정·환경 변경에 따라 교차점이 움직일 수 있다.

LSH는 비교 전에 shingle ID 변환, sparse row membership 구성, 서로 다른 shingle에 대한
120개 해시 계산, 모든 문서의 최솟값 갱신, 30개 band의 bucket 생성·중복 제거 비용을 낸다.
작은 n에서는 절약한 쌍 비교보다 이 준비 비용이 더 크다. 어휘 수가 5,000으로 제한된 데이터이므로
해시 계산 비용이 포화된 뒤에는 문서 수에 따른 signature 갱신 비용이 주로 증가한다.

### A2·A5 — 불편해진 크기와 메모리

처음 1분을 넘긴 크기는 n=8,000: 전수 비교 123.70s,
LSH 3.40s였다. 시간 대기가 먼저 불편해졌으며 메모리 부족은 관찰하지 않았다.
최대 n=8,000에서 전수 비교 peak 30.54 MiB,
LSH peak 62.27 MiB였다.

메모리는 입력 문서 생성 전에 tracemalloc을 켜서 측정한 Python 할당 peak이며 입력 데이터도 포함한다.
프로세스 RSS나 전체 시스템 RAM 사용량은 아니다. 시간은 `find()` 구간만 측정하고 데이터 생성은 제외했다.
tracemalloc 자체의 시간 비용이 있으므로 이 표의 시간과 tracing 없이 실행한 `bench.txt` 시간을
직접 비교하면 안 된다. 두 방법 모두 동일한 tracing 조건과 seed=246으로 측정했다.
